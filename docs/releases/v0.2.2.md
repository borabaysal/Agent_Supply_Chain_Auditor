# asca v0.2.2

A false-positive fix release, prompted by a real user's MacBook scan: 10 HIGH "secrets" in one agent transcript, and none of them was a secret.

## Fixed

### 🔑 A private-key header is no longer reported as a private key
- **Before:** the text `-----BEGIN … PRIVATE KEY-----` alone was enough. Documentation, checklists and secret-scanner regexes (e.g. `(RSA|OPENSSH|EC|DSA) PRIVATE KEY|AKIA…`) mention that header all the time; in one Codex transcript a single regex produced 9 HIGH findings.
- **Now:** asca requires base64 key material after the header. It looks on the same line, in the next lines of a file, in JSON-escaped transcript text and in quoted strings in source code (`"-----BEGIN …\n" "MIIE…"`). Encrypted legacy PEMs (`Proc-Type:` / `DEK-Info:`) are still recognised.
- **Benchmark:** across Hermes skills, community skills, real repos and a full Python `site-packages`, the old rule fired on 41 header lines; the new rule keeps the 25 that have a real key body (all genuine embedded test keys) and drops the 16 mentions.
- **Applies everywhere:** file scans, MCP definitions, allow rules and agent session history (plain-text, JSONL and Cursor SQLite).

### ☁️ AWS key IDs in pre-signed URLs are no longer reported
- An access key ID after `AWSAccessKeyId=` or `X-Amz-Credential=` is part of a pre-signed S3 link. The ID is public by design, and the link's signature expires. A link to a book preview PDF produced a HIGH "AWS access key" finding.
- AWS key IDs anywhere else are still reported.

## Upgrade notes
- **Fewer findings, never more:** expect some `secret.private-key` / `secret.session-history` findings to disappear. With `--telegram change`, that change in the failing set sends one message (possibly a FAIL → PASS).
- **Limit:** a truncated key that shows only its header (for example `head -1 id_rsa` output) is no longer reported.

**Tests:** 380 passing.
